# Native SQLite backup kernel

`backup.cpp` is a trusted native copy/validation component. JNI and private Android worker/Binder candidates now exist, but they are **not yet packaged/connected to a product launcher, the runtime backup port, publication or a usable product APK**. It accepts dedicated SQLite connections, never paths, SQL strings, descriptors from an Agent, provider metadata or credentials. Do not expose it as an Agent tool.

The source connection must be read-only and both connections must be outside any caller transaction. The destination must be a fresh private empty database that an Agent has **never held a writable descriptor to**. The kernel pins a read transaction before checking the source page budget, then uses the real `sqlite3_backup` API. A concurrent WAL writer may commit/grow the source while the chosen snapshot stays consistent.

Limits are 4 KiB–512 MiB for the snapshot budget and 1–30,000 ms for SQLite work/waits. An optional one-way atomic cancellation flag must remain alive until the function returns. Stable `BackupResult` values distinguish refusal, size, busy, timeout, cancellation, copy and integrity failure; no platform error text or database content is returned. SQLite work is interrupted by a joined native watchdog because the existing pinned build omits progress callbacks; its compile definitions are unchanged. These limits cannot bound an uninterruptible kernel I/O operation.

The function releases its read transaction and joins the watchdog before returning, including failure paths. The caller owns connection close. A successful result alone does **not** authorize publication: the Android owner must still verify active generation/cancellation, close the trusted writer, sync data/sidecars, publish durably through its held directory capability, independently validate/reopen read-only and issue only read-only snapshot grants. A publication with an unknown result must be reconciled, never retried automatically. This owner/IPC lifecycle and the upstream snapshot filesystem view remain unimplemented.

An Agent must not write a backup and later promise to discard its writable FDs. Duplicates cannot be revoked by closing an owner copy. The future trusted native owner must select the source and private destination itself; neither model input nor a guest path may choose them.

Host acceptance from the repository root:

```bash
python3 dsh-go/tooling/android-node-probe/test-sqlite-backup.py
```

The runner requires a complete Linux JDK (compiler plus JNI headers), discovered from `JAVA_HOME`/`javac`, or selected with `--java-home /path/to/jdk`. It verifies/extracts the source archive pinned by `android-node-probe/sqlite-runtime-pin.json`, keeps its compile definitions, and builds the real SQLite/VFS/kernel. It checks read-only admission, an actual cross-process WAL commit/growth after snapshot selection, an unchanged old snapshot, size/cancellation/busy/failure cleanup, integrity failure, no overwriting a nonempty destination and independent read-only reopening. In-memory destinations are used only for negative integrity/cancellation cases; the positive path uses eight real precreated file FDs and the writer receives only the four source FDs.

This is Linux host evidence. The pre-JNI core was subsequently compiled/linked for Android26 x86_64 and arm64-v8a on Windows at df0eeac (user-relayed evidence; see the shared cross-compile task). Android execution, JNI target linkage, UID enforcement, crash/power-loss publication recovery, production cancellation, ARM64 device use and real model requests remain **unverified**. The host VFS is still the verification adapter; this component does not turn it into a complete product filesystem.

## Granted-FD worker composition

`fd_backup.cpp::runGrantedSqliteBackup` composes admission, copy, close, file sync and an independently reopened read-only integrity check. It accepts exactly eight regular file FDs: the fixed source family and a fresh private snapshot family. It duplicates before inspecting, rejects wrong ownership, public/special permissions, links, repeated inodes, directories/pipes, unusable access/append flags and nonempty snapshot files. Caller descriptors remain owned by the caller. Only a successful reply's byte count is meaningful; failure does not imply an unwritten destination.

**Run this only in a fresh, one-shot trusted native worker process.** The owner PID must differ from the worker PID. A known existing FD VFS is refused before creating/closing aliases to its live SQLite files. Neither check substitutes for Android caller authentication or Main's source/destination policy. The expected UID/PID must come from trusted Main state, never model input. Do not call this in a long-lived Agent or Main SQLite process; alias closure could release unrelated POSIX file locks there.

Admission through teardown has a nonblocking process-local gate. A second call is refused before duplicating anything, including the interval where the first call has not registered its VFS yet. The host test deterministically pauses the first admission there and checks refusal of the competing call; process retirement is still required after the admitted operation.

The worker's VFS retains duplicate descriptors. After any admitted attempt the whole execution unit must retire, and Main must confirm that retirement before publication or read-only grants. The function does not attest process exit, publish a file, grant a capability, authenticate IPC or revoke already transferred FDs. Main must have synced the precreated file entries and private directory before handoff; the worker cannot sync a directory and never receives its descriptor.

The same host runner additionally executes separate seeding, invalid-grant, copying and read-only-check processes; its parent never opens SQLite. It verifies caller-FD preservation, same-worker reuse refusal, size/cancel refusal, sync failure, EINTR continuation and post-close integrity failure. Failed private output is discarded only after that test worker exits, and a fresh snapshot family is created for a subsequent independent attempt. GNU link-time faults affect only the host acceptance executable, not production code.

This composition is still **not connected to a product launcher or the guest backup/filesystem port**. A private Service/Binder candidate now exists as described below; it has not run on Android. A successful host worker is not a product runtime boot or proof of isolated Android UID behavior. The Node verification adapter remains a test dependency; a product native-library packaging path is also outstanding.

## JNI candidate (host verified, Android not wired)

`jni_backup.cpp` and `NativeSqliteBackupBindings.kt` define two fixed JNI methods: `run(int[8], ownerUid, ownerPid, maxBytes, timeoutMs)` and one-way `cancel()`. Neither accepts a path, SQL, a directory FD or a credential. An atomic process-lifetime claim permits only one invocation, even after bad input, cancellation or failure. The cancellation flag is never reset. A fixed three-long reply encodes explicit stage/result codes and candidate bytes; no platform exception/error text or database contents crosses this boundary. JNI allocation failure may throw rather than return a result; that never authorizes publication.

`SqliteBackupReply.decode` rejects wrong shape, unknown codes, impossible success/failure combinations and invalid byte counts. `candidateReady` means only that copying/sync/checks returned OK. It does **not** prove worker exit, active generation, durable publication or a read-only grant; a failure with zero bytes does **not** prove an unwritten destination.

The library must be loaded only by a fresh trusted native worker after authenticating Main and checking that the worker has a distinct isolated UID. Those Android checks are **not implemented by JNI itself**; the private Service candidate below implements them but still needs device verification. Do not load it from Main, Agent Node, an arbitrary shell or an Agent-callable tool. Owner UID/PID parameters are trusted policy inputs, not caller authentication. Android workers originate from zygote, so `getppid()` is not a way to discover Main. Preserve input FD ownership and confirm full worker retirement before publication, including JNI exceptions and cancellation.

The host runner now loads the real shared library in separate JVM processes using a Java fixture with the same binary class/native signatures as Kotlin. It tests eight inherited FDs, null/wrong-length arrays, invalid UID, owner-self PID refusal, pre-cancellation, repeated calls and an actual copied database independently reopened after worker exit. The exact Kotlin declaration and decoder also compile in the native boundary suite; four decoder cases cover finite failure codes, mutable-wire isolation, malformed replies and impossible success. JNI symbols must retain their binary names (App R8 keep rule added). This is **Linux JVM evidence, not an Android service, Binder caller check or device execution**. The separate NDK compilation task predates this JNI file and does not cover its target linkage.

## Private Android worker candidate (not product-connected or device-verified)

`SqliteBackupService` is declared non-exported, `isolatedProcess=true`, in its own `:sqlite_backup` process. It runs fixed native code only: no Node, interpreter, model tools, Key, path/SQL input, network endpoint or shell. Native loading happens only after checking actual `Binder.getCallingUid/getCallingPid`, rejecting the package/Main UID as worker UID, validating the request and receiving Main's peer acknowledgement. Identity is never taken from parcel UID/PID fields or zygote's parent PID. A manifest mistake hosting it in Main cannot load the native library or kill Main.

The private `SqliteBackupWire` ABI has START/CANCEL/RETIRE. START carries a 64-lowercase-hex nonce, bounded byte/time budget, a Main-owned callback Binder and exactly eight typed data PFDs. It has no path, extra fields, caller-selected native function or directory capability. The first authorized START consumes the worker even if malformed; retry requires a new process and Main's outcome policy. CANCEL/RETIRE require the same actual Main UID/PID and nonce. No controls or FDs may be given to Agent code.

The PEER callback is an **identity/admission handshake, not native readiness or runtime ready**. Main must verify actual callback Binder UID/PID, bind it to its expected service/nonce/generation, and acknowledge before native work starts. RESULT carries only the fixed candidate reply. Callbacks/result/death can arrive before the synchronous START acknowledgement; a future Main client must establish its state before sending START. Missing/late results, cancellation and caller-side timeouts never authorize an automatic retry or publication.

`SqliteBackupSession` guards one admission, caller identity/nonce, irreversible cancellation, native start, completion and retirement. A result arriving after cancellation/retirement cannot restore a candidate; beginning or finishing twice cannot reset the session. These are JVM policy tests, **not real Binder tests**. Main must still check its own active generation/cancellation when consuming any candidate, including cancellation racing after worker completion.

The Service links to Main callback death, keeps a hard lifetime timer, and self-kills on Main death, explicit retirement, expiry or completion. Cancellation before library loading is retained and forwarded after initialization; control threads do not close worker data FDs while SQLite is active. Worker-owned input copies close after the native operation; close failure suppresses the candidate. Native registry duplicates remain until process exit. The control Binder is held by a process-lifetime static anchor and is never intentionally detached to simulate death. **Main still has to observe that anchored Binder's death before considering publication/read-only grants**; ACK, RESULT, unbind, stopSelf or a timeout is not exit evidence. Android death/kill/FD behavior has not yet been exercised for this Service.

Main must send the data family exactly once and must not send any subsequent data FDs to this worker. Even rejecting a second Binder transaction cannot undo kernel-installed FD aliases; closing aliases while SQLite is active can release POSIX locks. This control Binder is a Main-only capability, never a public discovery/Agent API. The service is not a substitute for Main selecting the source, syncing private precreated destination entries, tracking identity/generation, waiting for retirement, durable publication/recovery and read-only grants.

Still missing: product native-library packaging, snapshot directory/publication policy, upstream snapshot FS and device acceptance. A Main client candidate now exists as described below. A bind without the packaged library fails closed and retires; the new manifest entry does not make the product runnable. The existing pre-JNI dual-ABI compilation and old 58-test Node APK do not cover this service.

## Main capability client (Android API compile + JVM policy, no device run)

`SqliteBackupClient.launch` checks Main/worker context, permits one outstanding attempt per process, retains duplicates of the eight Main-selected data FDs and a private Main-only directory capability, and acquires the directory's native advisory lease. The duplicate shares its open file description: a caller closing its own directory copy does not drop the client's lease. The directory is **never** sent to the worker. This is not source/destination selection: the future snapshot owner must supply the correct private family and directory, never Agent-provided descriptors. Neither this client nor its directory lock is a complete Main-crash recovery policy.

The client generates a fresh nonce, binds the explicit private service, links death before sending, and uses separate bounded background send/control queues. START is sent once. PEER/RESULT identities come from actual Binder UID/PID, not the payload; the admitted peer cannot be replaced. A matching result may arrive before the START reply, including a lost reply when the worker exits. Only a valid result plus anchored Binder death **and sender completion** can yield a candidate. Main owns no SQLite connection, but it still must not close/recycle data FDs while the sender uses them. Service disconnect/ACK/unbind/timeout alone is never retirement. A normal disconnect after self-retirement preserves the result while waiting for actual death.

`SqliteBackupExchange` tests those orderings, wrong identity/nonce, pre-send failures, ambiguous delivery, cancellation before/after a result, death before a late result, duplicate messages and rechecking a previously returned candidate. Cancellation invalidates received candidates; a timeout awaiting settlement returns UNKNOWN and does not fabricate a successful or unwritten outcome. Callers may wait again, never resend automatically. After possible transfer the client retains its copies/directory lease/global gate until actual death and sender completion. Framework disconnect does not clear them. The client retains itself through the binding/death/timer closures while pending.

`close()` cancels and requests self-retirement; it does not claim revocation or close live writer capabilities. After real settlement, client copies close and binding/subscription are released once. The caller still owns its original capabilities. `candidateStillValid` must be rechecked along with the owner's active generation/publication lock; it is not a publication permit. If an attempt remains UNKNOWN, do not publish/reuse/delete its private output. Across Main crash, unknown private staging families must be retained under unique names rather than guessed safe to sweep; old worker shutdown has not been proven to the new Main.

The exact client/Service and their 12 dependencies compile against the verified Android36 API jar, JVM17 target, with `-Werror`. Ten exchange policy cases join the native boundary suite (98 JUnit tests, 56 Node tests, all passing). Two temporary source-copy mutations removing either sender completion or death from the release condition fail the existing tests; repository sources were not replaced. **These are API compilation and host state tests, not real bind/UID/FD/death/cancellation execution on Android.** Product packaging, a concrete snapshot owner, native snapshot stage/publication primitives and the guest port remain pending.
