## 1. 交付状态：产品 APK 仍不可用

**没有可交付的 APK，也没有带引擎的 APK。** 原因是本轮把"为什么没有"查实了，不是时间问题：

- App 的 Android 构建需要 `dsh-go/runtime/out/<abi>/assets`（Linux rootfs + proot + Node + 引擎）。该产物由 `runtime/build-runtime.sh` 产出，而该脚本是 **Linux 宿主专用**。本机（Windows）编出来的 APK 能装能启动，但**没有引擎**。
- rootfs 目前**构建不出来**：Termux 已删除 `proot_5.1.107.98_*.deb`（404），仓库 pin 的是这个版本 → 见第 5 节。
- rootfs 里**还没有** mcode fork / 官方 Bot / host adapter —— 也就是说即使 rootfs 建出来，也仍缺第 4 节那三样。

## 3. 关键发现：产品里有两套 Bot 系统

- `lib/ui/bots/*` 与 `lib/state/bots_state.dart` 走的是 **`DsBotApi`**（DSH 引擎自带的 DS Bot 插件，经 `activeConnectionProvider` 连引擎）。
- 官方 mbot 的 `MiniMaxBotApi`（`packages/dsh_client`）**只被 dev 入口使用**。

产品决定是"复用官方 mbot 业务"，所以**引擎切换在 UI/状态层就是把这套从 `DsBotApi` 换成 mbot**，涉及状态模型与全部 Bot 页面 —— 不是"加个入口"就完事。上面的 transport 是这一步的前置条件。

另一处相关事实：**产品 App 里目前没有 Bot 入口**，Bot UI 只有 dev 入口能到。

## 4. runtime 接线仍缺的三样（与本轮无关，Linux 侧为主）

1. **rootfs 里没有 mcode fork / 官方 Bot / host adapter**：`build-runtime.sh` 只打包 Ubuntu base + Node + `@deepseek-ai/dsh` 引擎 + proot。
2. **正式 launcher 不存在**：生产代码里**没有任何地方调用** `RuntimeDescriptor.write` / `writeForTransfer`，所以 native 现在不会报出活服务，UI 会显示"没有 Bot 服务在运行"。launcher 落地时需调用 `BotRuntimeEndpoint.publish(...)` / `clear()`。
3. **设备侧无人启动 Bot 服务**：`startBotService` 目前只有宿主测试在调用。

## 5. 当前唯一的硬阻塞：proot 上游 pin 失效（Linux 侧）

Termux 已删除 `proot_5.1.107.98_*.deb`（pool 404），仓库 pin 的是这个版本：

```text
[runtime] error: Termux index no longer has proot 5.1.107.98 for x86_64 (bump the pin in build-runtime.sh)
```

实测：Termux 当前 x86_64/aarch64 都是 **proot 5.1.107.102**；源码包 `proot-v5.1.107.98.zip` 仍在且 sha256 与仓库 pin 一致；`proot-v5.1.107.102.zip` 也可用。需要在 `runtime/build-runtime.sh` 把 PROOT_VERSION bump 到 5.1.107.102 并更新 **3 个 sha256**（x86_64 deb、aarch64 deb、源码 zip）。这是**上游供应链变更**，不是这批提交引入的缺陷。仓库自己的约定：pin 变更要同时更新常量与文档并重跑验收命令。
